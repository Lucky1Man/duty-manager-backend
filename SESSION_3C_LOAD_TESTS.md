## Step 3 — Protocols.scala

`TARGET_URL` switches the entire test suite between architectures:
- Monolith: `http://localhost:8080`
- Microservices: `http://localhost:80`

```scala
package dutydesk

import io.gatling.core.Predef._
import io.gatling.http.Predef._

object Protocols {
  val baseUrl: String = sys.env.getOrElse("TARGET_URL", "http://localhost:80")

  val httpProtocol = http
    .baseUrl(baseUrl)
    .acceptHeader("application/json")
    .contentTypeHeader("application/json")
}
```

Authorization headers are added per-request from the feeder because each virtual user carries its own JWT.

## Step 4 — Feeders.scala

```scala
package dutydesk

import io.gatling.core.Predef._

object Feeders {
  // CSV columns: executorId,jwt
  // Generated by seed-data.sh
  val participantFeeder = csv("participants.csv").circular

  // CSV columns: templateId
  // Generated by seed-data.sh
  val templateFeeder = csv("templates.csv").random

  // Generates from/to pairs covering the last 30 days — no CSV needed
  val dateRangeFeeder = Iterator.continually {
    import java.time.LocalDate
    import java.time.format.DateTimeFormatter
    val fmt = DateTimeFormatter.ISO_LOCAL_DATE
    val to = LocalDate.now()
    val from = to.minusDays(30)
    Map("from" -> from.format(fmt), "to" -> to.format(fmt))
  }
}
```

## Step 5 — ScenarioA.scala — Write-Heavy

Stresses the write path. In microservices this also triggers a `participant-service` lookup, which is the overhead being measured.

```scala
package dutydesk

import io.gatling.core.Predef._
import io.gatling.http.Predef._
import scala.concurrent.duration._

object ScenarioA {

  val writeSteps =
    exec(
      http("Record Execution Fact")
        .post("/api/v1/execution-facts")
        .header("Authorization", "Bearer ${jwt}")
        .body(StringBody("""{"executorId":"${executorId}","templateId":"${templateId}"}"""))
        .check(status.is(201))
        .check(jsonPath("$.id").saveAs("factId"))
    )
    .pause(100.milliseconds)
    .exec(
      http("Finish Execution Fact")
        .patch("/api/v1/execution-facts/${factId}/finish")
        .header("Authorization", "Bearer ${jwt}")
        .check(status.is(200))
    )

  val scn = scenario("Write-Heavy: Record Execution Fact")
    .feed(Feeders.participantFeeder)
    .feed(Feeders.templateFeeder)
    .exec(writeSteps)
}
```

**Before running:** verify the finish endpoint path and HTTP method against the actual API. Adjust `patch`/`post` and the path to match the real controller.

## Step 6 — ScenarioB.scala — Read-Heavy

Stresses the read path. In microservices, resolving each fact's executor name requires N participant-service calls (one per fact on the page) — this is the N+1 HTTP call problem and the main overhead being measured.

```scala
package dutydesk

import io.gatling.core.Predef._
import io.gatling.http.Predef._
import scala.concurrent.duration._

object ScenarioB {

  val readSteps =
    exec(
      http("Get Execution Facts")
        .get("/api/v1/execution-facts")
        .header("Authorization", "Bearer ${jwt}")
        .queryParam("from", "${from}")
        .queryParam("to", "${to}")
        .queryParam("pageSize", "50")
        .check(status.is(200))
    )
    .pause(200.milliseconds)
    .exec(
      http("Get Templates")
        .get("/api/v1/templates")
        .header("Authorization", "Bearer ${jwt}")
        .check(status.is(200))
    )

  val scn = scenario("Read-Heavy: Get Execution Facts by Date Range")
    .feed(Feeders.participantFeeder)
    .feed(Feeders.dateRangeFeeder)
    .exec(readSteps)
}
```

    .randomSwitch(
      70.0 -> exec(ScenarioB.readSteps),
      30.0 -> exec(ScenarioA.writeSteps)

## Step 8 — DutyDeskSimulation.scala

Ramps from 50 to 200 concurrent users in three stages, sustaining each level for 5 minutes.

```scala
package dutydesk

import io.gatling.core.Predef._
import io.gatling.http.Predef._
import scala.concurrent.duration._

class DutyDeskSimulation extends Simulation {

  setUp(
    ScenarioC.scn.inject(
      rampUsers(50).during(60.seconds),
      constantUsersPerSec(50).during(5.minutes),
      rampUsersPerSec(50).to(100).during(60.seconds),
      constantUsersPerSec(100).during(5.minutes),
      rampUsersPerSec(100).to(200).during(60.seconds),
      constantUsersPerSec(200).during(5.minutes)
    )
  ).protocols(Protocols.httpProtocol)
   .assertions(
     global.responseTime.percentile(95).lt(2000),
     global.successfulRequests.percent.gt(99.0)
   )
}
```

Total duration per run: ~19 minutes.

## Step 9 — seed-data.sh

Hits the live API to register 20 test participants and 10 templates, then writes `participants.csv` and `templates.csv`. Must be re-run for each architecture because their databases are separate and the UUIDs will differ.

```bash
#!/usr/bin/env bash
# Usage: BASE_URL=http://localhost:80 bash seed-data.sh
# Run once against microservices, then again against the monolith before each test suite.
# Requires: curl, jq

set -e
BASE_URL="${BASE_URL:-http://localhost:80}"
OUT_DIR="src/test/resources"
mkdir -p "$OUT_DIR"

echo "Seeding against $BASE_URL"

# Get admin JWT
ADMIN_JWT=$(curl -sf -X POST "$BASE_URL/api/v1/auth/authenticate" \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@dutydesk.com","password":"Admin1-"}' | jq -r '.token')
echo "Admin authenticated."

# Register 20 test participants and collect their UUIDs + JWTs
echo "executorId,jwt" > "$OUT_DIR/participants.csv"
for i in $(seq 1 20); do
  EMAIL="loadtest$i@dutydesk.com"
  PASSWORD="LoadTest1!"

  curl -sf -X POST "$BASE_URL/api/v1/auth/register" \
    -H "Content-Type: application/json" \
    -d "{\"email\":\"$EMAIL\",\"password\":\"$PASSWORD\",\"firstName\":\"Load\",\"lastName\":\"Test$i\"}" > /dev/null || true

  RESPONSE=$(curl -sf -X POST "$BASE_URL/api/v1/auth/authenticate" \
    -H "Content-Type: application/json" \
    -d "{\"email\":\"$EMAIL\",\"password\":\"$PASSWORD\"}")
  JWT=$(echo "$RESPONSE" | jq -r '.token')

  # Fetch participant ID from profile endpoint
  ID=$(curl -sf "$BASE_URL/api/v1/participants/me" \
    -H "Authorization: Bearer $JWT" | jq -r '.id')

  echo "$ID,$JWT" >> "$OUT_DIR/participants.csv"
  echo "  Participant $i: $ID"
done

# Create 10 templates
echo "templateId" > "$OUT_DIR/templates.csv"
for i in $(seq 1 10); do
  ID=$(curl -sf -X POST "$BASE_URL/api/v1/templates" \
    -H "Authorization: Bearer $ADMIN_JWT" \
    -H "Content-Type: application/json" \
    -d "{\"name\":\"LoadTest Template $i\",\"description\":\"Template for load testing\"}" | jq -r '.id')
  echo "$ID" >> "$OUT_DIR/templates.csv"
  echo "  Template $i: $ID"
done

echo "Done. participants.csv and templates.csv written to $OUT_DIR/"
```

**Note:** If the `/api/v1/participants/me` endpoint path differs between architectures, adjust the script. The participant registration endpoint and auth response shape must match the actual API contracts.

## Step 10 — Running the Tests

### Against microservices

```bash
# Start microservices stack
cd ../duty-manager-microservices
docker compose up -d

# Seed test data
cd ../duty-manager-load-tests
BASE_URL=http://localhost:80 bash seed-data.sh

# Run Gatling (repeat 3 times, keep the median run)
TARGET_URL=http://localhost:80 mvn gatling:test \
  -Dgatling.simulationClass=dutydesk.DutyDeskSimulation

# Save results
cp -r target/gatling/* results/microservices/
```

### Against monolith

```bash
# Stop microservices, start monolith
cd ../duty-manager-microservices && docker compose down
cd ../duty-manager-backend && docker compose up -d

# Re-seed (different database, different UUIDs)
cd ../duty-manager-load-tests
BASE_URL=http://localhost:8080 bash seed-data.sh

# Run Gatling (repeat 3 times, keep the median run)
TARGET_URL=http://localhost:8080 mvn gatling:test \
  -Dgatling.simulationClass=dutydesk.DutyDeskSimulation

# Save results
cp -r target/gatling/* results/monolith/
```

During each run, Grafana at `http://localhost:3000` shows live metrics. Take screenshots at peak load (200 users, roughly 15 minutes in).
